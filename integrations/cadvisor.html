Monitor cAdvisor with Nightingale

Scrapes the cAdvisor built into kubelet or a standalone one for per-container CPU, memory, filesystem and network metrics; in kubelet mode it can attach Pod labels and annotations.

Last reviewed 2026-10-27

The cAdvisor input collects the container_* metrics that cAdvisor exposes: per-container CPU usage and throttling, memory working set and OOM events, filesystem reads and writes, network traffic and drops. Two ways to connect: type = "kubelet" scrapes the kubelet's /metrics/cadvisor (port 10250, authenticated) and can attach Pod labels and annotations to the metrics; type = "cadvisor" scrapes a standalone cAdvisor (port 8080 by default).

The dashboard shows resource usage per container and the metric reference explains each container_* metric. The rules cover CPU throttling, memory near the limit, OOM kills and network drops.

What's in the template​

  • 1 dashboard, 5 panels in total
  • 6 alert rules, each with runbook steps
  • 45 metric descriptions
  • Categraf collector config: input.cadvisor

How to connect​

  1. Install Categraf, put the config below in conf/input.cadvisor/cadvisor.toml, fill in your own address and credentials, and restart Categraf. The startup log prints input: local.cadvisor started once the plugin is loaded.

    # # collect interval
    # interval = 15

    [[instances]]
    # url = "https://1.2.3.4:10250"
    # type = "kubelet"
    ## url = "http://1.2.3.4:8080/metrics"
    ## type = "cadvisor"

    # url_label_key = "instance"
    # url_label_value = "{{.Host}}"
    # bearer_token_string = "eyJlonglongxxxx.eyJlonglongyyyy.oQsXlonglongZZZ"
    ## bearer_token_file = "/path/to/token/file"

    # ignore_label_keys = ["id","name", "container_label*"]
    ## choose_label_keys = ["id"]

    # timeout = "3s"

    # use_tls = true
    ## tls_min_version = "1.2"
    ## tls_ca = "/etc/categraf/ca.pem"
    ## tls_cert = "/etc/categraf/cert.pem"
    ## tls_key = "/etc/categraf/key.pem"
    ## Use TLS but skip chain & host verification
    ## insecure_skip_verify = true

  2. Open the integration center in Nightingale, find cAdvisor, and import the dashboards and alert rules into a business group.

  3. Imported rules start disabled. Check that the metrics are arriving first, then enable the rules one by one with thresholds that fit your environment.

Bundled alert rules​

6 rules. Each lists its trigger condition (PromQL) and the steps to take when it fires. Thresholds are meant to be adjusted after import.

Container memory approaching its limit​

S1 Critical · for 5 min · Trigger:

container_memory_working_set_bytes{name!=""} / (container_spec_memory_limit_bytes{name!=""} > 0) * 100 > 90

Runbook:

  1. Take name from the alert labels and run docker stats <name> or kubectl top pod to confirm live usage;
  2. Use the application's own memory analysis inside the container (jmap -histo:live for Java, pprof heap for Go) to separate normal growth from a leak;
  3. If the limit is simply too small, raise it and redeploy, adjusting the application's own heap ceiling to match (-Xmx must leave room for off-heap memory);
  4. If it is a leak, estimate the remaining runway from the growth rate and add an automatic restart as a stopgap while you investigate the code.

Container OOM killed​

S1 Critical · for 1 min · Trigger:

increase(container_oom_events_total{name!=""}[10m]) > 0

Runbook:

  1. Take name from the alert labels and confirm the OOMKilled state via the State.OOMKilled field in docker inspect <name> output or with kubectl describe pod;
  2. Run dmesg -T | grep -i 'killed process' to find the killed process and its memory usage at the time;
  3. Compare that usage against the limit and raise the limit if it is clearly too small;
  4. If usage looks abnormal, investigate it as a memory leak; for Java, -Xmx must be smaller than the container limit with room for off-heap memory or an OOM is guaranteed.

Container CPU heavily throttled​

S2 Warning · for 5 min · Trigger:

rate(container_cpu_cfs_throttled_periods_total{name!=""}[5m]) / (rate(container_cpu_cfs_periods_total{name!=""}[5m]) > 0) * 100 > 25

Runbook:

  1. Take name from the alert labels and confirm the growth of nr_throttled and throttled_usec with cat /sys/fs/cgroup/cpu.stat (cgroup v2);
  2. Compare actual CPU usage against the limit; being throttled while below the limit usually means bursts are being sliced up by the 100 ms period, so raise the limit slightly or lower in-period concurrency;
  3. A common trigger is a JVM or Go runtime sizing thread pools from the host core count; set GOMAXPROCS or -XX:ActiveProcessorCount to match the limit;
  4. If more compute is genuinely needed, raise the CPU limit and watch the throttling ratio fall.

Container filesystem usage too high​

S2 Warning · for 5 min · Trigger:

container_fs_usage_bytes{name!=""} / (container_fs_limit_bytes{name!=""} > 0) * 100 > 85

Runbook:

  1. Take name and device from the alert labels and run docker exec <name> du -sh /* 2>/dev/null | sort -rh | head to find the biggest consumers;
  2. In the vast majority of cases application logs are not being rotated: configure logrotate or switch to writing to stdout and let the runtime rotate them;
  3. If the writable layer is filling up, mount a volume for directories that need persistence rather than writing into the layer;
  4. As an emergency measure run docker system prune to reclaim host space from unused images and stopped containers.

Container restarting repeatedly​

S2 Warning · for 5 min · Trigger:

changes(container_start_time_seconds{name!=""}[1h]) > 3

Runbook:

  1. Take name from the alert labels and run docker logs --tail 200 <name> or kubectl logs --previous to read the logs from before the last exit;
  2. Run docker inspect <name> and check State.ExitCode and State.OOMKilled in the output to distinguish an OOM, a deliberate application exit, and a failing health check;
  3. Handle OOMKilled as a memory alert; for a non-zero exit code, find the start-up failure in the application logs (missing configuration, dependency not ready);
  4. If a health check is the cause, confirm the probe's initial delay is longer than the real start-up time and raise the start period if needed.

Container network receive packet drops​

S3 Info · for 5 min · Trigger:

rate(container_network_receive_packets_dropped_total{name!=""}[5m]) > 1

Runbook:

  1. Take name from the alert labels and run docker exec <name> cat /proc/net/dev plus ss -s to check drops and queue state;
  2. If the receive queue is overflowing, raise the kernel's net.core.netdev_max_backlog and the application's accept queue (somaxconn);
  3. Check whether the host NIC is also dropping packets (ethtool -S <nic> | grep -i drop); if the problem is at the host level, do not chase it inside the container;
  4. If traffic genuinely exceeds the container's networking capacity, evaluate switching to host networking or raising the bandwidth allocation.

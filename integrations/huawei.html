Monitor Huawei Cloud with Nightingale

Scrape Cloud Eye (CES) metrics converted to Prometheus format by the cloudeye-exporter; templates cover ECS, RDS, DCS, ELB, Kafka, RocketMQ, CSS and WAF.

Last reviewed 2026-10-13

Huawei Cloud metrics come from the Cloud Eye service (CES). The cloudeye-exporter maintained by Huawei Cloud converts CES metrics per product namespace into Prometheus metrics named huaweicloud_sys_<service>_<metric>, which the Categraf prometheus input scrapes.

The templates are split by product: ECS hosts, RDS (MySQL and PostgreSQL), DCS Redis instances and proxy nodes, ELB, distributed messaging (Kafka, RabbitMQ, RocketMQ), Cloud Search (CSS/ES) and WAF, one dashboard each. The rules cover ECS CPU and memory, RDS connections and disk, DCS memory and hit ratio, ELB backend health; the metric reference explains each product's metrics one by one.

What's in the template​

  • 14 dashboards, 330 panels in total
  • 35 alert rules, each with runbook steps
  • 286 metric descriptions

How to connect​

Deploy the cloudeye-exporter and configure it with an IAM account's AK/SK, the project and the namespaces to collect. Once http://<exporter>:8087/metrics?services=SYS.ECS responds, scrape it per namespace with the Categraf prometheus input:

# conf/input.prometheus/huaweicloud.toml
interval = 120

[[instances]]
urls = ["http://<exporter>:8087/metrics?services=SYS.ECS,SYS.RDS,SYS.DCS,SYS.ELB"]
labels = { job = "huaweicloud" }

Cloud Eye metrics are at 60-second granularity or coarser, so do not collect more often than that.

  1. Open the integration center in Nightingale, find Huawei Cloud, and import the dashboards and alert rules into a business group.
  2. Imported rules start disabled. Check that the metrics are arriving first, then enable the rules one by one with thresholds that fit your environment.

Huawei Cloud ECS CPU usage exceeds 80%​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_cpu_usage >80

Runbook:

  1. SSH in and use top -H to find the busiest processes and threads;
  2. Use perf top or a language profiler to find the hot functions;
  3. Tell business growth apart from a code fault (infinite loop, frequent GC);
  4. For growth, change to a larger flavour in the console or scale out horizontally.

Huawei Cloud ECS inode usage exceeds 80%​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_SlAsH_disk_inodesUsedPercent >80

Runbook:

  1. Run df -i to find the mount point;
  2. Count files level by level to find the directories with the most small files;
  3. Common sources are log fragments, session files and container layers — confirm and bulk delete;
  4. Longer term, consider moving small-file workloads to a dedicated partition.

Huawei Cloud ECS NTP offset exceeds 1 second​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_ntp_offset > 1000

Runbook:

  1. Run chronyc tracking to check the offset and upstream source state;
  2. Huawei Cloud ECS should use the internal NTP service (ntp.myhuaweicloud.com) — confirm it is configured;
  3. Start chronyd if it is not running and enable it at boot;
  4. For a large offset, use chronyc makestep to step the clock.

Huawei Cloud ECS TIME_WAIT connections exceed 20000​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_net_tcp_close > 20000

Runbook:

  1. Run ss -s to see the real connection state distribution;
  2. Run ss -tan | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn to find the peers;
  3. The root cause is usually too many short-lived connections — switch the application to long-lived connections or a pool;
  4. As an emergency measure enable net.ipv4.tcp_tw_reuse and widen ip_local_port_range.

Huawei Cloud ECS zombie processes above 0​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_proc_zombie_count >0

Runbook:

  1. Run ps -ef | awk '$2 ~ /Z/ || $8 ~ /Z/' or ps aux | grep 'Z' to find the zombie processes and their parent PPIDs;
  2. Once you have the parent, the problem is that it never calls wait() — this must be fixed in code;
  3. As an emergency measure restart the parent so init reaps the zombies;
  4. If the count keeps growing, the code fix is mandatory — restarting is only a stopgap.

Huawei Cloud ECS available memory below 20%​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_mem_available < 20

Runbook:

  1. Run free -h to check available memory and swap;
  2. Run ps aux --sort=-%mem | head to find the largest consumer and judge whether it is leaking;
  3. For a leak, capture a heap in the application — a restart alone is not enough;
  4. For growth, change to a larger memory flavour in the console.

Huawei Cloud ECS outbound packet loss rate exceeds 50%​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_net_dropout > 50

Runbook:

  1. Run ip -s link show to confirm TX dropped is growing;
  2. Confirm whether the instance flavour's bandwidth cap is saturated — cloud bandwidth is capped per flavour and exceeding it drops packets;
  3. If capped, adjust bandwidth or change the flavour in the console;
  4. If not capped, check security groups, the kernel transmit queue and the application's send logic.

Huawei Cloud ECS outbound packet error rate exceeds 50%​

Huawei Cloud ECS disk write IOPS too high​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_agt_SlAsH_disk_agt_write_requests_rate > 99

Runbook:

  1. Run iostat -x 1 to check actual IOPS and await;
  2. Run iotop -oP to find the process writing the most;
  3. Compare against the EVS disk type's IOPS ceiling to see whether it has topped out — ultra-high performance and general purpose disks differ greatly;
  4. If it has, upgrade the disk type or expand it in the console (IOPS usually scales linearly with capacity); if not, optimise the application's write pattern.

Huawei Cloud Redis average CPU usage exceeds 80%​

This metric samples the CPU usage of the measured object multiple times within the statistics period and reports the average. Only single-node/primary-standby/read-write-splitting instances are supported.

S2 Warning · for 2 min · Trigger:

huaweicloud_sys_dcs_cpu_avg_usage > 80

Runbook:

  1. Run SLOWLOG GET 10 to find the slowest commands;
  2. Focus on O(N) commands such as KEYS, HGETALL and SMEMBERS and on big-key operations, switching to SCAN or batching;
  3. Check whether an RDB/AOF persistence run is causing the CPU spike;
  4. If it stays high after tuning, upgrade the instance flavour in the console.

Huawei Cloud Redis memory usage exceeds 80%​

S1 Critical · for 2 min · Trigger:

huaweicloud_sys_dcs_memory_usage > 80

Runbook:

  1. Use redis-cli --bigkeys to find large keys and split them or add TTLs;
  2. Use INFO memory to check the fragmentation ratio and enable activedefrag if it is high;
  3. Check whether keys without an expiry keep accumulating;
  4. Confirm maxmemory-policy, then expand the flavour in the console.

Huawei Cloud Redis slow log detected​

S2 Warning · for 1 min · Trigger:

huaweicloud_sys_dcs_is_slow_log_exist == 1

Runbook:

  1. Run SLOWLOG GET 10 for the specific slow commands and their timings;
  2. Focus on O(N) commands and big-key operations;
  3. Switching to SCAN with batching and splitting large keys is the real fix;
  4. If the slow commands come from a scheduled job, move it to off-peak hours.

Huawei Cloud Redis bandwidth usage exceeds 90%​

This metric samples the CPU usage of the measured object multiple times within the statistics period and reports the average. Only single-node/primary-standby/read-write-splitting instances are supported.

S2 Warning · for 2 min · Trigger:

huaweicloud_sys_dcs_bandwidth_usage > 90

Runbook:

  1. Use INFO stats to check instantaneous_input_kbps / output_kbps and determine the direction;
  2. Use redis-cli --bigkeys to find large keys — reading and writing large keys is the most common cause of saturated bandwidth;
  3. Split large keys and reduce one-shot bulk reads;
  4. If you genuinely need more bandwidth, upgrade the flavour in the console.

RocketMQ broker down​

S1 Critical · for 1 min · Trigger:

huaweicloud_sys_dms_broker_alive == 0

Runbook:

  1. Confirm the instance and broker state in the Huawei Cloud console;
  2. Confirm clients have failed over to other brokers — with multiple brokers only some partitions are unavailable;
  3. If the console looks fine but clients report errors, check the network and security groups plus the client's nameserver address;
  4. If it stays unavailable, open a ticket with Huawei Cloud.

RocketMQ per-core CPU load exceeds 1.5​

S1 Critical · for 3 min · Trigger:

huaweicloud_sys_dms_broker_cpu_core_load > 1.5

Runbook:

  1. Check that broker's TPS and message backlog curves in the console to tell producer-side from consumer-side pressure;
  2. For a heavy consume backlog, scale out consumers first;
  3. For a produce spike, evaluate upgrading the instance flavour;
  4. Confirm no oversized messages or huge batch sends are overwhelming the broker.

S1 Critical · for 3 min · Trigger:

huaweicloud_sys_dms_broker_memory_usage > 85

Runbook:

  1. Check the message backlog in the console — a backlog consumes significant memory;
  2. Restoring consumption to drain the backlog is the most direct fix;
  3. Check whether the message retention period is set too long;
  4. For sustained growth, upgrade the instance flavour.
